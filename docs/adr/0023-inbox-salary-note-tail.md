# ADR-0023: 收件箱薪资以 pipeline.md note 尾段为事实源

- **Status:** Accepted (2026-09-14)
- **Context:** 需求「在收件箱页面显示薪资数据，可以按薪资过滤」。薪资数据现状：探索页采集卡片携带 salaryText（各站口径折算见 CONTEXT.md「薪资文本」词条），ADR-0021 确认入管时随 note 落库（`原 note · salaryText`，或解析不出时 `原 note · 薪资未知`）——pipeline.md 没有专用薪资列（CONTEXT.md「见过台账」同此缺口）。要在收件箱显示/过滤/排序薪资，两个来源选项：给 pipeline.md 加专用薪资列（动 data contract，影响所有写入路径，历史行要迁移），或从 note 解析（零迁移，但 note 是自由文本，用户可手写，全文扫描会把「周三面试 35K 岗」这类内容误读成薪资）。

## Decision

2026-09-14 与用户逐条确认的五条：

1. **事实源 = note 尾段**：仅当行 note 以「 · 」分隔的末段恰好是确认入管写入的形态（salaryText 原文，或「薪资未知」标记）时才认。用户手写的 note 段永不被解析为薪资。解析复用探索页现成逻辑（browser-search.mjs 的清洗与月薪 K 折算）。
2. **不加专用薪资列**：data contract 不动，无历史行迁移。
3. **过滤沿用「薪资下限」语义**：区间重叠判定、薪资未知放行并打标（「不误删」取向），与探索页完全一致；控件为数字输入框（月薪 K），复用探索页 i18n 文案；过滤状态存 localStorage，跟随 ADR-0010 收件箱 triage 状态的持久化惯例。
4. **排序**：FacetChips 区加「按薪资」切换——开 = 按解析区间中位值降序、薪资未知沉底；关 = 默认新鲜度。收件箱的 SINGLE ORDER PLUG POINT（单一比较器插点）不变，薪资排序只是该插点的另一比较器。
5. **作用范围仅收件箱 tab**：追踪器表格不动——其薪资来自评估报告研究而非采集卡片，口径不同，不混用。

## Consequences

- **note 尾段成为事实上的薪资查询面**。未来若改用专用列，需双源兼容期（列优先、note 尾段兜底）加一次性迁移；在此之前，用户手改 note 尾段即改薪资——这是接受的代价：尾段严格匹配使这种改动可见、可预期，静默误读不存在。
- **旧行 / 手写 note 的行没有尾段薪资** → 一律按「薪资未知」处理（放行、打标、排序沉底），与 salary_filter「无薪资数据不误删」取向一致。
- **解析在服务端 readInbox 完成**（labeled segment 已在此解析），`InboxJob` 新增携带薪资字段；客户端只做展示、过滤与排序。
- 收件箱的薪资过滤语义与探索页共用同一 glossary 词条（「薪资下限」），两处 UI 行为保持一致是后续改动的约束。
