# ADR-0048: 简历页面历史版本（.bak 即历史，抽屉浏览 + 还原即生效）

- **Status:** Accepted (2026-09-21)
- **Context:** web 端简历页面 `/cv` 编辑 `cv.md`（user-layer、gitignored，无 git 恢复兜底）。保存走 `POST /api/cv`，经 `atomicWriteWithBackup`（`safe-write.ts`）在覆盖前把旧内容快照为根目录 `cv.md.bak-{ISO时间戳}`（冒号/点替换为连字符）。该机制运行至今已积累 8 份快照，但：
  1. **无入口**——没有任何 UI/接口能列出、预览、还原这些快照；它们只是"崩溃备份"语义的沉睡文件。
  2. **无清理**——每次保存新增一个文件，无限累积。
  3. **误还原即丢当前**——若直接用旧快照覆盖，当前版本没有任何机制保证先被留住。
  
  需求（用户原话口径）：「点击保存时，上一次保存的简历就是历史」「简历历史可用于还原，不支持编辑」「可设为当前版本」。
  
  术语：**快照** = `cv.md.bak-{ts}` 文件；**历史版本** = 快照在 UI 中的呈现；**还原** = 把某快照内容设为当前 `cv.md`。

- **Scope:** `web/src/app/api/cv/route.ts`（保存后清理超限快照）、`web/src/app/api/cv/history/route.ts`（新，列表 + 单份内容）、`web/src/components/cv/cv-history-drawer.tsx`（新，抽屉面板）、`web/src/components/cv-editor.tsx`（历史入口 + 还原接线）、`web/src/lib/i18n/clusters/cv.ts`（中英文案）、`web/tests/lib/cv-history*.test.mjs`（新）。**不改动**：`safe-write.ts` 的 `backup()`/`atomicWriteWithBackup()` 通用函数及其他 4 个消费路由（profile/portals/followups/title-filter）的行为；`POST /api/cv` 的写入语义（还原复用它，后端零新增写路径）。

## Decision

1. **历史 = 现存 .bak 快照，零迁移**：`GET /api/cv/history` 直接扫描根目录 `cv.md.bak-*`，解析文件名时间戳倒序排列，附字节数。不建历史目录、不建 JSON 索引——磁盘上已有的 8 份历史立即可用，快照产生机制一行不改。
2. **单份内容接口带严格校验**：`GET /api/cv/history?ts={时间戳}` 返回该快照内容用于预览；`ts` 必须完整匹配 `\d{4}-\d{2}-\d{2}T[\d-]+Z` 白名单格式并重组文件名（拒绝任意路径拼接，防遍历）。
3. **UI = 抽屉面板**：保存按钮旁新增「历史版本」入口（带份数徽标），点击弹出侧边抽屉：左列快照列表（相对/绝对时间 + 字节数），右侧只读 markdown 预览，每条带「还原」按钮。不挤占编辑区。
4. **还原即生效，走现有保存路径**：前端把选中快照内容经现有 `POST /api/cv` 提交。由此天然获得：当前版本先被 `backup()` 快照进历史（还原可逆）→ 原子写入 → 触发决策 5 的清理。后端不需要 restore 端点。还原前二次确认；编辑器有未保存修改（dirty）时先提示。
5. **20 份保留上限，仅 cv.md**：`POST /api/cv` 保存成功后清理超限的最旧 `cv.md.bak-*`（保留最近 20 份）。清理逻辑只挂在 cv 保存路径，不进通用 `backup()`——本次需求只提简历，不扩大影响面。
6. **诚实边界**：历史仅覆盖 web 端保存；CLI intake、AI 直改 `cv.md` 不产生快照。抽屉内以说明文案注明。
7. **i18n**：文案进 `clusters/cv.ts`，跟随现有 useI18n 机制，中英双语。

## Alternatives considered

- **迁移到 `data/cv-history/` 专用目录**：根目录更整洁、可带元数据，但需要一次性迁移且旧 .bak 依然存在形成双数据源；收益不抵成本。否。
- **JSON 索引记录保存元信息**：与 .bak 文件冗余，多一个可失真的状态文件。否。
- **还原填入编辑器、待手动保存**：多一步确认，与「还原不支持编辑」的预期相悖；且还原即生效方案下当前版本已自动入历史，可逆性不输。否。
- **通用 `backup()` 内做 20 份清理**：profile/portals 等文件一并改变行为，影响面超出需求。否。
- **下拉菜单直接还原 / 页面常驻列表**：前者无预览能力，后者常驻占空间。均否。

## Consequences

- `.bak` 文件语义从「崩溃备份」升级为「版本历史」，但文件名、产生时机、产生方式完全不变——已有消费者（如有）无感。
- 快照数量首次有界（20 份），磁盘不再无限累积；历史文件单份几十 KB，列表与清理成本可忽略。
- 现存 8 份历史无需任何操作即可浏览/还原（tolerant reader，无迁移）。
- 还原动作本身会在历史里新增一条「还原前快照」——这是特性不是噪音：用户在历史间来回切换天然自洽。
- `POST /api/cv` 每次保存多一次目录扫描 + 可能的 unlink，量级为个位数文件操作，可忽略。
