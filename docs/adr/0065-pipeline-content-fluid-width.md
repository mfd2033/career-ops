# ADR-0065: 管道页内容区宽度自适应——去掉居中宽度上限，两个 tab 统一铺满

- **Status:** Accepted (2026-09-26)
- **Context:** 需求（2026-09-26，一轮 grilling 敲定）：「web 端，求职管道页面右侧改成宽度自适应」。现状与约束：

  1. **管道页内容区被两级居中上限收窄**：外层容器 `mx-auto max-w-6xl`（72rem ≈ 1152px，`pipeline-view.tsx`）；收件箱 tab（默认 tab）内部再收一道 `mx-auto max-w-3xl`（48rem ≈ 768px，`inbox-triage.tsx`）。宽屏下内容居中、两侧留白，且同一页切 tab 时内容宽度跳变（768 ↔ 1152）。
  2. **详情页已经是全宽**：`/pipeline/{n}` 的 `ReportView` 用 `w-full`（无上限）——列表页是这一族表面里唯一还带居中上限的。
  3. **用户硬件事实**：主显示器 1920×1080、100% 缩放（2026-09-26 会话实测）。最大化的内容区可用宽度 ≈ 1920 − 240（侧栏）− 48（左右 padding）≈ 1632px，比现上限多出约 480px。
  4. **表格是 10 列信息密集型**（ADR-0064）：只把容器拉宽，会让列被拉宽而公司/职位名仍在旧截断上限（16rem/22rem）处截断，列内出现死白——文本列上限必须作为配套一起动。
  5. **本页布局另受两条既有 ADR 约束**：ADR-0011 的整页定高/列表内部滚动、ADR-0039 的常驻槽位——两者都只约束「高度与滚动」，本 ADR 只动宽度，与其正交。

- **Scope:** `web/src/components/pipeline-view.tsx`（外层容器 + 公司/职位列上限）、`web/src/components/inbox/inbox-triage.tsx`（根容器）、本 ADR、ADR-0011 文末「延伸」标注。**不动**：详情页（已全宽）、其他页面的宽度上限（home/explore 5xl、jobs 4xl、config 2xl 等维持现状）、表格 `min-w-[60rem]` 与窄窗口横向滚动行为、移动端（<768px）行为、任何高度/滚动布局。

## Decision

1. **内容区整体放开、不封顶**（Q1+Q3）：外层容器去掉 `mx-auto max-w-6xl`，收件箱根容器去掉 `mx-auto max-w-3xl`——两个 tab 一律铺满「左侧栏右侧的全部可用宽度」。不引入新的宽度上限常量：封顶值（1920/1600px）在当前 1920 屏上永不触发或几乎不可见，属于「为想象中的硬件付现实复杂度」；未来真上超宽屏再评估。
2. **文本列上限配套放宽**（Q4）：公司列 16rem → 24rem、职位列 22rem → 32rem。理由：列宽了截断点不跟走就是列内死白；两列本就是信息密度最高、最该吃空间的两列。数值是起点值，截图验收时按 1632px 目视微调（ADR-0064 决议 11 的「截断不换行、行高恒定」口径不变）。
3. **`min-w-[60rem]` 与移动端行为不动；窄窗横滚状态不变、幅度略增（实测修正）**：`min-w-[60rem]`（960px）保留；`<768px` 视口本来就不受 max-w 影响。「窄窗口零变化」在实测中被推翻——1440/1280/1200 档原本就横滚，横滚量因公司列上限放宽而 +95~128px（表格内容宽 1322 → 1450px，增量全部来自公司列 16rem → 24rem）；1536 档容器同时变宽（1102 → 1231px），溢出 220 → 219px 几乎不变；**1920 档从横滚 220px 变为完整显示（无横滚）**——这是本次改动最直接的收益。
4. **验收口径**（Q5）：Playwright 在 1920 / 1536 / 1280 三档宽度 × 收件箱、表格两个 tab 截图，另补 1200px 一档抽查横向滚动边界；`npm --prefix web run typecheck` + `npm --prefix web test` 全绿。截图交用户目视确认后收工。

## Alternatives considered

- **封顶 1920px / 1600px**：给未来超宽屏留安全阀，但当前 1920 屏上永不触发（或仅 32px 留白），是当前无收益的魔法数字，否。
- **只放开表格区、收件箱保持 max-w-3xl**：改动更小，但同一页切 tab 的内容宽度跳变（768 ↔ 1632）比现状更刺眼，用户明确选「两个 tab 统一」，否。
- **数据列定宽 + 文本列吸收全部剩余空间**（最规整的表格布局）：视觉最专业，但要给 7 个数据列定宽并重调 `min-w` 体系，窄窗回归面大；本次取渐进方案（只放宽文本列上限），若截图目视难以接受再另议，否。
- **列上限不动、只改容器**：列被拉宽而名字仍在旧上限截断，列内死白——「放开」被内层上限吃掉的半吊子状态，否。
- **让表格自适应收窄以消除窄窗横滚**：用户的诉求是宽屏留白，不是窄窗横滚（Q1 明确排除）；且 10 列数据表收窄必然挤压内容，否。
- **顺带统一其他页面的宽度策略**：超出本次需求（用户只提管道页），且各页面上限是按内容形态定的（配置 2xl、工作器 4xl），一刀切反而不对，否。

## Consequences

- 1920 屏上内容区从约 1152px 变为约 1632px（+41%）；收件箱与表格两个 tab 的宽度自此一致（切 tab 不再跳变）。
- **已知残差 1**：收件箱行全宽后，行内信息（左侧）与「保存/跳过」按钮（右侧）的水平距离变远——这是「整体放开」的直接代价，用户已知情接受。
- **已知残差 2**：数据列（分数/薪资/体检/用时/状态/日期/来源）随容器拉伸变宽、列内留白略增；若日后难以接受，可另议「数据列定宽」方案（见 Alternatives）。
- 文本列上限（24/32rem）是起点值，验收截图时可能微调；上限只影响「内容比列宽更长的极端行」的截断位置，不影响行高。
- 窄窗口横滚状态不变（原本就横滚）但幅度略增：1440 档 +95px、1280/1200 档 +128px（详见落地状态实测表）；移动端（<768px）自然滚动不受影响。
- 本 ADR 只覆盖管道列表页；详情页（已是全宽）与其他页面的宽度上限维持现状，不因本次改动产生任何预期外的联动。
