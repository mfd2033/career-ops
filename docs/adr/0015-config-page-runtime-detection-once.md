# ADR-0015: 配置页运行时检测「每浏览器一次」+ 手动重检

- **Status:** Accepted (2026-09-11)
- **Context:** web 配置页每次 mount 都 `fetch("/api/clis")` 触发服务端 `detectClis()` 真查——Windows 上是 PATH + 一组候选目录（含 npm 全局 `node_modules` 递归）的同步文件系统扫描，opencode 还可能 spawn `opencode models` 子进程（该子进程结果有 1 分钟缓存，检测本身无缓存）。每次打开配置页都付出同样的目录扫描延迟，而检测结果（这台机器装了哪些运行时）在一次会话内几乎从不变化。非配置页消费方 `resolveCliId()`（jobs/apply 在用户从未保存配置时的兜底）也调同一端点，同样每次真查。用户决策：**配置页只在首次打开时自动检测一次，之后一律手动**。

## Decision

1. **「已检查过」的判定单位是浏览器，不是服务进程**（Q1）。localStorage 新独立 key `career-ops:clis` 存 `{checkedAt, clis}`，**key 存在即「已检查」标记**；配置页 mount 时读到可解析的缓存就直接渲染、不发请求，读不到（首次/被清除/解析失败）才自动检测一次。以浏览器为单位的理由：检测结果对单用户单机是准静态事实，浏览器缓存即用户视角的真值；服务端生命周期方案会在每次服务重启后再自动查一次，违背「以后不再自动检查」的规则；TTL 方案过期后变相恢复自动检查，同样违背。
2. **检测失败不落「已检查」标记**（Q3）。请求出错或响应不可解析时视为未检查，下次打开配置页仍自动检测——否则一次网络抖动就让用户永远看到空列表，只能靠发现手动按钮自救。
3. **服务端 `detectClis()` 加进程内缓存，所有消费方共享**（Q2）。`GET /api/clis` 无参走缓存（首次请求填充），`?refresh=1` 强制失效、真查、回填。`resolveCliId()` 不改代码，兜底调用自动命中缓存后成本趋近于零。缓存放 lib 层而非前端，是因为「只改配置页」会让 apply 兜底继续每次真查，没省到该省的成本，且两套调用路径会出现不一致的检测结果。
4. **`refresh=1` 同时重置 opencode 模型列表的子进程缓存**。手动重检的语义是「真查一次」——若复用 1 分钟 TTL，一分钟内的重检会拿到旧模型列表，违背直觉。
5. **手动重检是缓存的唯一失效途径**。cli 模式三态（检测中/空/列表）下都渲染状态行「上次检测：{时间} · 重新检测」；空态（一个都没装）恰恰是最需要重检入口的场景（用户刚装好工具）。时间用 `Intl.DateTimeFormat` 绝对短格式（Q5），不引相对时间库。
6. **缓存渲染路径与真查路径行为完全一致**（Q4）：「唯一已装 CLI 自动保存 cliId」的幂等逻辑在渲染缓存时同样执行，避免两条路径下拉行为分裂。
7. **范围边界**：本决策只约束配置页；`resolveCliId()` 在从未保存配置时的兜底检测保持现状（它可能触发进程内缓存的首次填充，属一次性初始化而非重复检查）。

## Alternatives considered

- **服务端生命周期缓存（重启后自动重查一次）**（Q1 否决）：「首次」的语义最干净，但服务重启后再自动查违反「以后不再自动检查」；且「已检查过」状态落在服务端，用户无法跨重启保持。
- **TTL 缓存（如 24h）**（Q1 否决）：过期后下次打开又自动查，等于变相恢复自动检查；新鲜度收益极低（运行时安装是月级事件）。
- **塞进现有 `career-ops:config` 对象**（Q1 否决）：该 key 语义是「用户偏好」，检测结果是「机器事实」；混存会让清除配置误删检测缓存，8 个 CLI 的完整模型列表也使偏好对象臃肿。
- **只改配置页前端，`/api/clis` 不动**（Q2 否决）：apply 兜底仍每次真查；两套调用路径可能拿到不一致结果。
- **独立 `POST /api/clis/refresh` 端点**（Q2 否决）：语义重复，GET + 查询参数幂等且少一个端点。
- **相对时间（"3 小时前"）**（Q5 否决）：需手写分档逻辑，绝对时间零依赖且双语直接走 Intl。

## Consequences

- 配置页二次打开零网络请求，首屏即时渲染；代价是检测结果可能过时——新装运行时后下拉里看不到，必须点「重新检测」。
- 未来维护者会看到 mount 不 fetch、看起来像遗漏——这是故意的（本文档存在的原因），别把自动检测加回去。
- 服务端缓存意味着 `resolveCliId()` 的兜底检测在一次进程生命周期内最多真查一次。
- localStorage 缓存跨「服务端重装过运行时」的情况会失真，由手动重检兜底；清除站点数据则回到首次自动检测。
