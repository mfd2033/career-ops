# ADR-0085: 投递时机建议——三平台黄金时间矩阵、纯函数引擎与管道页常驻条（Kaneo CO-44）

## 状态

Accepted (2026-10-20)

## 背景

需求（Kaneo 任务 CO-44，高优先级）：「根据各个平台的简历投递黄金时间矩阵提供投递时间建议」。附件《投简历黄金时间指南-20261010》已把 Boss直聘 / 猎聘 / 智联招聘 的时段规律整理成三张矩阵表，但这份知识目前只活在附件里——用户要在「现在该不该投、投哪个平台、下一个窗口是几点」上做判断，仍得回去翻文档。

既有事实与约束：

1. **三个平台的行为根本不同**：Boss直聘是直聊模式，晚间 20:00–22:00 与周末都是活跃高峰；猎聘/智联是邮箱式投递，只认工作日 HR 在后台筛简历的时段，非工作时段投递会被积压。同一句「现在能投吗」对三个平台必须分开回答——合成一个全局结论会把两者都答错。
2. **矩阵是日历函数，不是随机经验**：每张表都是「时段 × 日型」→ 等级（最佳/可以/避开）。同一时刻在不同日型下结论不同（周二 10:00 猎聘最佳，周六 10:00 猎聘避开）。因此判定必须是 `f(平台, 本地时刻)` 的纯函数，不能缓存成静态文案。
3. **判定必须在本地时钟上算**：本产品是本地优先单机应用，web 服务与浏览器同机同时区；引擎按 `Date` 的本地时间取值，不引入时区库、不做 UTC 换算。
4. **落点必须贴着「投递决策点」**：批量视角在管道页 `/pipeline`（今天该投哪些），单份视角在报告详情页 `/pipeline/{n}`（这一份投不投）——后者正是「申请」按钮所在的屏。首页/分析页/探索页都不做投递决定，放上去就变成又一次需要主动想起来去点的地方。
5. **布局是定高+滚动（ADR-0011/ADR-0039/ADR-0065）**：管道页 `md:` 以上是 `h-screen flex-col`，任何条件出现/消失的行都会把表格顶开。建议条必须常驻槽位、固定高度，不能「有结论才出现」。
6. **组件无测试面（ADR-0077 同款约束）**：可测逻辑全部下沉到纯 `.mjs`，用 `node --test` 门；UI 靠 typecheck + build + 手测。
7. **附件还写了假期策略与「新岗位 24–48 小时内优先」**：前者需要节假日日历（数据源与年度维护都在仓外），后者不是时段问题。二者本 ADR 明确排除，见「后果」。

## 决策

1. **新增纯引擎 `web/src/lib/delivery-window.mjs`**（零依赖、客户端安全，与 `weekly-pace.mjs` 同层同风格）：
   - 数据：`BOSS_WINDOWS` / `OUTBOUND_WINDOWS`，每行 `{start, end, levels:[mon, midweek, fri, weekend]}` 分钟数 + 等级数组；猎聘与智联共用一套矩阵（附件第三节原文即「规律一致，共用一张」）。
   - 日型映射 `dayTypeOf(date)`：周一 `mon`、周二~周四 `midweek`、周五 `fri`、周六周日 `weekend`。
   - 判定 `windowAt(platform, date)` → 当前分钟落在哪一行、等级为何。
   - 前瞻 `nextWindow(platform, from, {levels, horizonDays})` → 从 `from` 起 7 天内在矩阵里出现的第一段目标等级窗口；`from` 已落在目标窗口内则返回该窗口本身并标记 `current: true`。
   - 汇总 `summarize(now)` → 三平台各自的当前等级 + 下一段黄金窗口，外加一个全局动作码 `send | ok | wait`（任一平台 `best` → `send`；否则任一 `ok` → `ok`；否则 `wait`）。
   - 原文未列的时段按「避开」处理（Boss 00:00–07:00）：依据是指南第五节「别在周五下午、深夜、假期中随手投」。
2. **等级 = 三值枚举 `best | ok | avoid`，不在引擎里出现任何人类文案**：文案全部走 i18n（新语料簇 `web/src/lib/i18n/clusters/delivery.ts`，en+zh），引擎只回码，避免第二份中文口径。
3. **入口 = 管道页页头（三平台）+ 报告详情页操作区（只该报告来源平台）**，同一枚 `DeliveryTimeHint`：
   - `/pipeline` 页头：标题行与 tabs 之间常驻一条，给出「当前时刻 + 全局结论 + 三平台等级 + 下一段黄金窗口」——这是「今天该投哪些」的批量视角，三平台并列才有意义。
   - `/pipeline/{n}` 与 `/report/{n}` 报告详情页：挂在分数/建议徽章下面的**操作区正下方**，且**只算该报告来源平台**（例：来源猎聘就按猎聘矩阵判，不拿 Boss 的晚间时段去建议一份猎聘的职位）。平台从报告 header 的 `**URL:**` 经 `source-label.mjs` 的 `sourcePlatform()` 还原（与列表页「来源」列同一套域名映射，不另建一张表）；来源不在三平台（拉勾/ATS/公司官网…）时**不献成三平台、也不静默消失**，而是明说「该职位来源不在 Boss直聘/猎聘/智联，暂无投递时段规律」。两条路由共用 `ReportView`，挂在组件层一次覆盖，深链页自动同享。
   - 详情页**不渲染平台徽章**（只有窗口文案 + 结论）：「猎聘 · 可以」只是把这一页已知的来源再重说一遍；徽章只在列表页的三平台并列里才有信息量。
   - 单平台视角下把「当前窗口 09:30–11:00」紧跟在时刻后面（不是行尾），而不换成「下一段黄金」：正在黄金时，用户真正想知道的是「还能投到几点」；多平台（列表页）仍用 `ml-auto` 在行尾收尾。
   - 三处共用同一个组件与同一份引擎，没有第二套口径；文案全部走 i18n（新语料簇 `web/src/lib/i18n/clusters/delivery.ts`，en+zh），引擎只回码。
   悬停 title 给出判定依据与数据来源（指南 2026-10-10）。
4. **客户端自算，不新增 API**：组件挂载后用本机 `Date` 计算，并每 30 秒重算一次；服务端首帧渲染固定高度的占位（`—`），避免 hydration 文案不一致，也避免「建议条出现→表格下移」的位移（ADR-0039 的槽位原则）。
5. **徽章配色复用既有语义**：`best → Badge tone good`、`ok → muted`、`avoid → warn`；品牌橙继续留给「选中/激活」，不参与等级编码。
6. **建议只描述时机，不触发任何写操作**：不自动改状态、不自动投递、不生成提醒；它是只读提示，与「Ethical Use」一致。

## 被拒方案

- **三平台合成一个「现在能不能投」**（否决）：Boss 晚间/周末有效、猎聘/智联无效，合并后的结论必有一半是错的。
- **「列表每行给出该行来源平台的投递建议」**（否决）：行级建议要先把「来源 → 平台」对齐（未知平台、ATS 职位没有平台），且同一平台的行结论完全相同，等于把一句全局文案复制 N 份；页头一条覆盖全部行。
- **详情页也列三平台**（否决）：一份猎聘职位的投递动作只发生在猎聘；把 Boss 的晚间黄金并列上去就是拿别家的规律做建议，用户很容易照着错的窗口去投。平台可从报告 URL 确定，那就只给那一个。
- **来源不可识别时默默隐藏整条或强行套三平台**（否决）：隐藏会让人以为功能坏了，强套就是编；两者都差于一句「该来源没有已知规律」。
- **把矩阵作为配置项放进 `config/profile.yml`**（否决）：矩阵是平台方行为规律、不是用户偏好，配置化只会让口径分叉；真需要改，改引擎数据表并配测试。
- **服务端 API `/api/delivery-window`**（否决）：结论只依赖本机时钟，加一层 HTTP 只是把同样的纯函数挪远，还引入服务端/客户端时钟不一致的可能。
- **引入节假日日历实现「假期策略」**（本版否决）：数据源与每年维护都在仓外，先把稳定可证的日历规律落地；假期规则在指南里仍可人工查阅。
- **文案写进组件里**（否决）：与全站 i18n 双语文案惯例冲突，且会破坏 en/zh 键对称。

## 后果

- 正面：「现在投不投、投哪个」从翻文档变成抬头一眼；列表页看三平台、详情页只认该职位来源平台，两处共用同一枚组件与同一份引擎；零新增写面、零新增 API、零新增依赖。
- 代价一：矩阵是三平台行为规律的快照（指南 2026-10-10），平台策略变化时需手动更新数据表——已由测试把每条规律写成断言，改矩阵会立刻看到哪条口径变了。
- 代价二：建议按本机时钟计算，跨时区（如给海外岗位投递）不在覆盖范围；页面文案已明示这是国内三平台的规律。
- 已知边界一：节假日（国庆等）策略未实现——假期中仍会按「工作日/周末」给出结论，与指南第四节不一致；用户需自行按假期规则调整。
- 已知边界二：引擎只看时段，不看「新岗位 24–48 小时内优先」这类与发布时刻相关的规则。
- 回滚：新增文件（引擎/测试/i18n 簇/组件）+ 管道页一处挂载，删掉即回到原状；无数据迁移。

## 修订记录

- **2026-10-26 — 新增台账表行级「投递时机」列（推翻本 ADR「被拒方案」第 2 条）**：用户要求在 `/pipeline` 台账表的「薪资」列右侧增加一列「投递时机」，逐行显示该职位来源平台在当前时刻的可投结论（best/ok/avoid）。原否决理由（「同一平台的行结论完全相同，等于把一句全局文案复制 N 份；页头一条覆盖全部行」）在实操中被权衡掉：用户明确要把结论就近放进决策点（与薪资/分数并列的另一列），而非只在页头抬头看。
  - 单一口径不破：行级列与页头 `DeliveryTimeHint` **复用同一引擎**（`delivery-window.mjs` 的 `windowAt`）与同一「来源 → 平台」映射（`source-label.mjs` 的 `sourcePlatform`）；等级 → 语义色复用从 `delivery-time-hint.tsx` 导出的 `LEVEL_TONE`，不新建第二套翻译/配色口径。
  - 列形态：纯展示、不参与排序（结论是实时时钟量，排序无意义），紧随薪资列插入；非三平台来源（拉勾/ATS/公司官网）显示「—」，悬停走 `delivery.noSource` 如实说明没有规律。
  - 时钟纪律同页头条：只在浏览器算，首帧 `now=null` 走「—」占位（避免 hydration 不一致），每 30 秒重算；按平台等级（而非 `now` 引用）下发到行，跨窗口边界时结论才真正翻面，`memo` 行不白白重渲染。
  - 影响面：`web/src/components/pipeline-view.tsx`（列头/列体/时钟）、`web/src/components/delivery-time-hint.tsx`（导出 `LEVEL_TONE`）、`web/src/lib/i18n/clusters/pipeline.ts`（新增 `pipeline.col.deliveryTiming`），测试 `web/tests/lib/delivery-window.test.mjs` 增补接线守卫。
