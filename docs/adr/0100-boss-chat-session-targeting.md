# ADR-0100: 自动跟进在 BOSS 聊天页按招聘者定位会话，核验对象后才发送

## 状态

Proposed (2026-11-12)

## 背景

「自动跟进」（`/followups` 行操作 ⚡）上一轮已落地：用户在弹窗里确认并改好话术，扩展把这一条填进招聘站聊天框、点一次发送、回读校验，再把渠道/联系人/备注/未读回填成一条记录。真机冒烟三站，猎聘通过，智联未验，**BOSS 六次尝试全部发不出去**。

现场证据（扩展失败时回传的 `detail`，输入框 ±120px 内的可点节点，压缩成一行）：

```
clicked | DIV.friend-content-warp|昨天郭女士数字马| ; SPAN.name-text|郭女士| ; DIV.gray last-msg|[送达]您好，我|
```

由此定下三条事实：

1. BOSS 的职位详情页点「继续沟通」后落到 `https://www.zhipin.com/web/geek/chat`，**这个 URL 不带任何会话标识**，页面上同时摆着左侧会话列表和右侧聊天区。
2. 该页在**没有任何会话被指定**时，右侧会默认打开一条既有会话。冒烟那次打开的是「郭女士 · 数字马力」，与目标行不是同一家。也就是说：此刻若真把话术填进编辑器并点发送，**这条跟进会发给错误的人**。
3. 上一轮只做了止损：`scoreInputCandidate` 里 `bottomGap > 720` 直接判死，BOSS 不再往搜索框里写字，如实报 `no-input`。这解决了填错地方，没解决发不出去，BOSS 至今一条都没成。

另外两条环境约束，决定了方案不能靠调试逼近：

- BOSS 反调试：一开 DevTools 就整页刷新，页面结构的唯一观测通道是 `detail` 回传。
- BOSS 没有公开的会话 URL 契约，`/web/geek/chat` 实测不带会话参数；私有参数会随改版失效，而且失效时无从核验。

结论：BOSS 要能发，得先答出「发给谁」，而且要在发送之前答出来。发送后回填不算答案。

## 决策

1. **发送前先定身份。** 弹窗确认阶段新增「发给谁」输入框（招聘者姓名），默认值取该行最近一条跟进记录的联系人（`entry.followups` 末条非空 `contact`），没有历史就留空。空值时 BOSS **不出自动发送按钮**，只给「复制话术 + 打开职位」。猎聘/智联不要求填（打开职位页即进入对应会话），填了也只用于回填。
2. **身份随消息体下传，SW 不解释字段。** `followup-send` 消息扩为 `{ url, text, expectContact }`；background 只负责找 tab、转发、原样回传结果，不参与身份判断（与「单点判定在纯逻辑层」一致）。
3. **定位只在 BOSS 且页面是会话列表页时发生。** 判定顺序：先按既有 `findInput` 找聊天框；找到就直接走原来的填写-发送链路；找不到且 `location.pathname` 是 `/web/geek/chat` 时，进入定位流程：采集左侧列表候选（每项只取结构化特征：名字文本、预览文本、矩形、类名），交给纯逻辑层打分：
   - 姓名归一化后相等 +4，姓名被包含 +3；
   - 公司名命中 +2；
   - 职位名命中 +1。

   通过条件三条同时成立：最高分 ≥ 3（必须有姓名命中）、最高分严格大于第二名、命中项唯一。任一不成立即报 `ambiguous-target`（有候选但不唯一）或 `no-target`（一条都没有），**绝不点第一项兜底**。
4. **点开会话后必须核验当前会话对象。** 等待聊天区出现，再读会话头部对象（名字 + 能读到的公司），与目标身份做同一套归一化包含匹配。不通过 → 报 `contact-mismatch`，**不填字、不点发送、不落库**；读不到头部对象 → 报 `no-counterpart`，同样不发。宁可失败，不可发错。
5. **失败原因码扩四个**：`no-target` / `ambiguous-target` / `contact-mismatch` / `no-counterpart`，进 `REASON_CODES` 与 `followups.autoReason.*`（en+zh）。所有失败都附 `detail`：候选会话的名字与公司 token 压成一行（最多 12 条），用户据此改名重试。这是 BOSS 上唯一可用的排障通道，沿用它。
6. **纯逻辑与 DOM 分工不变**：`followup-send-pure.js` 新增 `normalizeName`、`scoreConversationCandidate`、`pickConversationCandidate`、`verifyCounterpart`；`followup-send.js` 新增 `conversationCandidates()`、`openConversation()`、`readCounterpart()`。web 侧只加字段、传参、i18n 与按钮可用性，**不在 web 层加任何站点特例**。
7. **一次一条、不重试、不批量**的边界不变。定位点击属于导航（可重试一次等懒加载），发送本身仍然只有一次。

## 被拒方案

- **列表第一项兜底**（否决）：冒烟事故正是「默认会话」造成的。兜底等于把发错人变成默认行为。
- **给会话行写固定选择器**（否决）：三站没有公开 DOM 契约，改版即失效；且失效时点错的分支比找不到更贵。候选一律走特征打分。
- **按职位名匹配会话**（否决）：列表行主要展示招聘者与公司，职位名不稳定出现，同名职位跨公司重名多，命中率与准确性都不可靠。
- **从职位详情页抓招聘者姓名当目标**（否决，本轮不做）：可读性未验证；一旦抓错或抓到推荐位人名，就是发错人。身份由用户确认，来源可追溯。
- **用 URL 深链直达某个会话**（否决）：`/web/geek/chat` 无会话标识，私有参数随改版失效，且失效时无法核验当前对象。
- **让扩展自己读 `data/follow-ups.md` 取联系人**（否决）：扩展读不到仓库文件，且这会把数据层写入口子开到浏览器侧。
- **核验放宽成「有聊天区就算对上」**（否决）：这次事故就是这样，聊天区一直在，错的只是对象。

## 后果

- 正面：BOSS 从「一条都发不出去」变成「对象对得上才发」；发错人这一类事故在发送前被拦住；失败原因可读、可据此改名重试。
- 代价：BOSS 首次跟进必须先有姓名（用户输入或历史记录），否则只能走复制+打开；`郭女士` 与全名之类的称呼差异会导致 `no-target`，需要用户按 `detail` 里的候选改名。这点摩擦是故意留的，换掉的是发错人的风险。
- 已知边界：会话头部读不到对象时一律不发（`no-counterpart`），BOSS 上可能出现「明明选对了却发不出去」。属于诚实失败，不在本轮放宽。
- 回滚：撤掉定位步骤与 `expectContact` 即可回到 ADR-0081 + 上一轮实现的状态（BOSS 恒报 `no-input`），纯增量，无数据迁移。
