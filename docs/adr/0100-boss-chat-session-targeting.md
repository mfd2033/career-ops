# ADR-0100: 自动跟进在 BOSS 聊天页只发「本次从岗位页点进去的那条会话」

## 状态

Proposed (2026-11-12，修订版)。初版（同日、提交 `704d80d`）设计成「按招聘者姓名在会话列表里定位」，被用户指正后重写；本版不新增界面、不做会话定位。

## 背景

「自动跟进」（`/followups` 行操作 ⚡）的发送链路是：打开该行职位的详情页 → 点「立即沟通 / 继续沟通」→ 把话术填进聊天框 → 点一次发送 → 回读校验。真机冒烟三站，猎聘通过，智联未验，BOSS 六次尝试全部发不出去。

现场证据（扩展失败时回传的 `detail`，输入框 ±120px 内的可点节点，压成一行）：

```
clicked | DIV.friend-content-warp|昨天郭女士数字马| ; SPAN.name-text|郭女士| ; DIV.gray last-msg|[送达]您好，我|
```

初版据此推断「右侧打开的是别人的会话，这条跟进会发给错误的人」，于是设计了「先填招聘者姓名 → 在会话列表里按名字定位 → 核验会话对象」。用户指出了这条推断的问题：从岗位详情页点「继续沟通」打开的聊天窗口，本来就是该岗位的招聘者。

复核证据支持用户：`#1282` 的公司是「小猎吧」，那是猎头，冒烟时右侧的「郭女士 · 数字马力」正是它代招的客户，不是「另一家公司的人」。而原始 `detail` 只覆盖输入框 ±120px，当时命中的是被误当成聊天框的**顶部搜索框**，快照里根本没有右侧会话，所以「发错人」从来没有证据。

真正的事实只有一条，且是结构性的：BOSS 的 `/web/geek/chat` 不自带会话标识，如果扩展把这条页面当成发送目标、不追究是怎么进来的，那右侧是谁就发给谁。

## 决策

1. **不引入「发给谁」字段，不做会话列表定位。** 发送链路保持不变：岗位详情页 → 点继续沟通 → 填字 → 发送。会话由 BOSS 在点「继续沟通」时绑定到该岗位，扩展不干预、不猜。
2. **加一道到达判定。** 内容脚本记录本次运行里有没有点过「立即沟通 / 继续沟通」跳进聊天页；只有「页停在 `/web/geek/chat` 且本次没点进去」时才拒绝发送，报 `unknown-target`。这道判定的目的只有一个：杜绝「聊天页是别处带来的，就照发不误」。
3. **拒绝时什么都不做。** 不填字、不点按钮、不落库，弹窗里给出原因与排障提示（从岗位页点继续沟通再试）。
4. **判定口径不动**：`sent` 仍然要求「输入框清空 + 聊天流回显」两项都成立；`uncertain` 不当成已发送、不自动勾「对方未读」；一次一条、不重试、不批量、不代投。
5. **改动面收在内容脚本内**：`followup-send.js` 记录 `clickedChatEntry`、加 `isConversationListPage()` 与失败分支；`background.js` 不参与判断；web 侧只多一个原因码文案。

## 被拒方案

- **按招聘者姓名定位会话**（初版设计，否决）：用户实测路径已经保证会话正确，再要求填姓名，是把一件本来能成的事变成可能失败，还平白多一层输入与一个失败原因。
- **列表第一项兜底**（否决）：兜底等于把「发给谁」交给页面默认行为，正是本轮要排除的形态。
- **给会话行写固定选择器 / URL 深链**（否决）：BOSS 没有公开的会话 URL 契约，私有参数随改版失效，失效时无从核验。
- **从岗位详情页抓招聘者姓名反向校验**（否决，本轮不做）：可读性未验证，抓到推荐位人名反而更糟。
- **「有输入框就发」不加任何门槛**（否决）：页面若被别处带到聊天页，对象不明；一道到达判定成本极低。

## 后果

- 正面：不新增界面与数据结构；BOSS 能否发送，收敛成一个可验证的事实——「继续沟通」这一跳有没有被点到、点完右侧是不是该岗位的会话。
- 代价：万一 BOSS 把聊天页开在别的标签页、或岗位页没有「继续沟通」按钮，本轮会诚实地报失败（`no-input` / `unknown-target`），不会绕过。
- 已知边界：会话对象仍由 BOSS 决定，扩展只能确认自己是从该岗位的入口进来的，不能证明右侧是谁。真要证明，需要另行设计（且需先有稳定的会话标识）。
- 回滚：删掉到达判定与 `unknown-target` 文案，即回到上一轮实现。
